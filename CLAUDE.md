# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Natural deduction proof assistant for classical, intuitionistic and modal propositional logic: Java 21 / Spring Boot backend (multi-module Maven) plus a React 19 / TypeScript / Vite frontend. `docs/` has longer prose docs (`docs/API.md` is the REST reference); when they disagree with the code or the poms, trust the code.

## Commands

Backend (run from repo root):

```bash
mvn -B clean install                 # build everything + unit tests + ITs
mvn -B verify                        # what CI runs (unit tests, then *IT.java in the executable module, incl. the one that boots the packaged fat jar)
mvn -pl domain/proof-structures/implementation.deduction.classic -am test                 # one module (-pl takes directory paths)
mvn -pl domain/proof-structures/implementation.deduction.classic -am test -Dtest=ClassicAndTest   # one test class
mvn -pl executable -am verify -Dtest=RestServiceIT -Dsurefire.failIfNoSpecifiedTests=false        # the Spring integration test
mvn -B test-compile org.pitest:pitest-maven:mutationCoverage    # mutation testing (CI job; skipped inside `executable`)
java -jar executable/target/executable-0.1-SNAPSHOT.jar         # serves the API and the UI on :8080 (the build embeds the UI, see below)
```

Frontend (from `frontend/`):

```bash
npm ci                        # use ci, not install; node_modules can be left over from the old react-scripts setup
npm start                     # vite dev server; proxies /logic to localhost:8080, so start the backend jar too
npm test                      # jest --coverage
npx jest src/components/menu  # a single test file/dir
npm run typecheck             # tsc --noEmit; `vite build` does not type-check
npm run build                 # outputs to frontend/build (NOT dist)
```

CI (`.github/workflows/`) has no lint step. Run the full Maven `verify` and `npm run typecheck` + `npm test` locally before pushing.

Every PR adds one bullet to `CHANGELOG.md`, under the current month's release (`## sep-26`) and its Added/Changed/Fixed/Removed heading, ending with the PR number. The `work-next-issue` workflow does this with the `changelog-entry` skill (`.claude/skills/changelog-entry`). `plan.md` keeps only the pending steps; the finished ones live in the issues, the PRs and the changelog.

## Architecture

**Backend layering** (`domain/` is framework-agnostic except the use-case config classes, which are Spring `@Configuration`s):

- `domain/logic-language/`: formula ASTs. `framework` defines generic operators (`Conjunction`, `Implication`, `Negation`, ...); `implementation` (classical) and `implementation.modal` subclass them and each provide a parser (built on javaluator). Modal adds `Always`/`Sometime`/`Until` and relation formulas (`Equals`, `LessEqual`). `implementation.firstorder` (package `com.dan323.expressions.firstorder`, served as `"first-order"`) is first-order logic with equality: terms (`VariableTerm`, `FunctionApplication`; no infix operators, a binary operation is a named function symbol like `m(x, y)`), `Predicate`, `Equals`, the `*FirstOrder` connectives, `Forall`/`Exists`, and a hand-written recursive-descent `FirstOrderParser` (javaluator cannot read binders or undeclared function symbols). Its formulas have `freeVariables()` and capture-avoiding `substitute(var, term)`, and are `equals`/`hashCode` up to renaming of bound variables (`Alpha` compares canonical forms); `toString()` prints `forall x. A` and is read back by the parser.
- `domain/proof-structures/`: `framework.deduction` has the generic `Proof<T,Q>`, `ProofStep`, `ProofReason`, `Action`/`AbstractAction` and the generic rule bases (`AndI`, `ModusPonens`, `DeductionTheorem`, ...). `implementation.deduction.classic` / `.modal` bind those to a concrete language: `NaturalDeduction` / `ModalNaturalDeduction`, one `Classic*`/`Modal*` class per rule, `ParseClassicalAction`/`ParseModalAction`, and an automatic solver. Rules validate with `isValid(proof)` then mutate with `apply(proof)`. Steps are never removed on discharge, only `disable()`d. `implementation.deduction.firstorder` (packages `com.dan323.proof.firstorder` and `.proof`) binds them to the first-order language: `FirstOrderNaturalDeduction` (plain `ProofStep`s, so the usual text layout; `automate()` runs `FirstOrderAutomate`, see below), one `FirstOrder*` class per shared rule, `ParseFirstOrderAction` (the 14 shared rule names plus the classical aliases, `ruleName`), and the rules `∀E` (line + term), `∀I`/`∃I` (line + target), `∃E` (line; discharges the innermost subproof as `<>E` does), `=I` (term; printed `=I` with no lines, which `ProofReason.parseReason` cannot read, so `ParseFirstOrderAction.parseReason` handles it) and `=E` (equation line, line, target). `Instances` holds their side conditions: `instanceOf` (is B `A[x:=t]`, and for which t) and `isReplacement` (is B `A` with some `s` replaced by `t`); both rename bound variables to unused names, so capture is refused. The `∀I`/`∃E` freshness checks use `FirstOrderNaturalDeduction.isFreeInOpenAssumption` (valid `Ass` steps, i.e. premises and open assumptions). A `∀E` step's term is not written down: `parse()` recovers it with `instanceOf`.
- `domain/use-cases/`: `model` (DTOs `ProofDto`/`StepDto`/`ActionDto`/`ActionDescriptorDto`), `base-use-case` (`ActionsUseCases`, `Transformer` DTO<->domain, `ProofParser` text->proof, `LogicalApplyAction`, `LogicalSolver`, the exceptions, and `ActionsUseCaseConfiguration`), plus `classical-use-case` (which also holds intuitionistic logic, package `com.dan323.uses.intuitionistic`), `modal-use-case` and `first-order-use-case` (package `com.dan323.uses.firstorder`).
- `rest/`: `framework` has the single `ControllerInterface` (`/logic/{logic}/actions|action|solve|proof|exercises|theories`) and `RestExceptionHandler`; `model` has the request/response records (`ProofActionRequest`, `ProofResponse`, `ErrorResponse`).
- `executable/`: Spring Boot app. It also serves the built frontend as static files from `classpath:/public/`.

**How a new logic plugs in:** each logic's use-case module exposes `Transformer`, `ProofParser` and `LogicalGetActions` beans, keyed by a logic-name string (`"classical"`, `"intuitionistic"`, `"modal"`, `"modal-next-until"`, `"first-order"`). `ActionsUseCaseConfiguration` collects all beans of those types into maps keyed by `logic()`. The URL `{logic}` path segment picks the entry. So adding a logic means adding modules plus a `*Configuration` that is imported in `executable/.../ApplicationConfiguration`. A logic can also be a rule filter on top of another one, like `"intuitionistic"` (`IntuitionisticConfiguration` in `classical-use-case`): it reuses the classical language, rules and parser, and its `Transformer`/`ProofParser`/`LogicalGetActions` subclass or filter the classical ones to drop every `AvailableAction` whose `isIntuitionistic()` is false (only `NOTE`, the `-E` rule); such a proof or action is a 400. Its transformer and parser build an `IntuitionisticNaturalDeduction` (`com.dan323.classical.proof`, a subclass of `NaturalDeduction`, which is not `final`) whose `automate()` runs `IntuitionisticAutomate` (`com.dan323.classical.internal`). It and `ClassicalAutomate` are subclasses of `GoalDirectedAutomate`, the goal-directed engine of the old classical solver (intro rule for the top goal, else the elimination rules, else push a subgoal and assumption; stop when a round changes nothing), whose hooks decide whether `-E` is an elimination rule, what to do with a goal that no rule of its shape reaches (`updateOtherGoal`: classical assumes `- goal` and aims for `FALSE`), what to do when a round changes nothing (`stalled`) and a size bound (`withinBounds`). `ClassicalAutomate` must produce exactly the proofs it did before the split: `ClassicalSolverRegressionTest` compares them with `classical-solver-proofs.txt` (written by the original solver). `IntuitionisticAutomate` has no `-E` and no proof by contradiction; a goal no introduction rule reaches gets attempts instead, in this order: a case split on a valid `A | B` step (reach `A -> G` and `B -> G`, then `|E`), each side of a disjunction goal, backwards through a valid `A -> G` step (reach `A`, then `->E`), and ex falso (reach `FALSE`, then `FE`; only when some valid step has a negation or `FALSE` in it). The engine's `reachGoal` hook (`null` for classical) applies those last rules. A failed attempt rolls back (rebuilds the proof from its premises by replaying the kept steps, and restores the goals) and the next one is tried; a successful one is never revisited. An attempt never nests inside one of the same kind on the same formula, and the proof plus goals are kept below `STEPS_PER_SYMBOL` times the size of the premises and goal, so it always stops (the engine itself never applies `->E` to an identity implication `B -> B`, which `OrE1`/`OrE2` leave in the proof and which used to make it loop, issue #192; the bound is a second line of defence). It is not complete: on failure it resets the proof to its premises, and `done` false may also be the answer for an intuitionistic theorem (`IntuitionisticSolverTest` lists the known ones; it solves every intuitionistic exercise). A logic may also expose a `LogicalExercises` catalog (`GET .../exercises`; a known logic without one answers `[]`) and a `LogicalTheories` list (`GET .../theories`, `TheoryDto{id, name, premises}`: named premise sets; likewise `[]` without one). Each `Exercise` keeps a reference solution in the proof-text layout that is never sent to clients; `ClassicalExercisesTest`/`IntuitionisticExercisesTest`/`ModalExercisesTest`/`ModalNextUntilExercisesTest`/`FirstOrderExercisesTest` replay every one, so a new exercise must come with a solution that parses and is done (a modal one must also derive its goal in `s0`: the modal `Proof.isDone()` ignores the state, so the test checks it; the `modal-next-until` `isDone()` already requires `s0`).

**`"first-order"`** (`FirstOrderConfiguration`, package `com.dan323.uses.firstorder` in `first-order-use-case`) serves the `implementation.deduction.firstorder` proofs. Its solver (`hasSolver()` true) is `FirstOrderAutomate` (`com.dan323.proof.firstorder.internal`, not exported), a best-effort bounded version of the intercalation calculus of Sieg and Byrnes (Studia Logica 1998, the AProS proof search): it searches a tree of derivations (`FirstOrderAutomate.Node`) with iterative deepening and only then writes it as steps (`Emitter`, which validates every action and cites a formula already in scope instead of deriving it again). Per goal: close the available lines under the eliminations that need no choice (`&E`, `->E`, `-E`, `FI`, `∀E` with the terms of the proof up to `MAX_TERM_DEPTH`, `=E` for symmetry and transitivity only), then the invertible introductions (`&I`, `->I`, `-I`, `∀I` with a new name, `=I`), then `∃E` (new name) and `|E` (committed), then `|I`/`∃I`, `->E` with a missing antecedent, `FI` on a `- A` for `FALSE`, and proof by contradiction. New names are never reused within one search, so the `∀I`/`∃E` side conditions hold wherever a derivation is written. It stops on `MAX_DEPTH`, `CALL_BUDGET` and `WORK_BUDGET` (counts, not time), and resets to the premises when it finds nothing. `FirstOrderSolverTest` (domain and use-case modules) checks it solves every pure exercise and `group-identity-unique`; the other group exercises need rewriting inside terms and end `done=false`. `AvailableFirstOrderAction` describes 20 actions: the 14 shared rules under their modal names (classical aliases accepted through `ParseFirstOrderAction.ruleName`) plus `∀I`, `∀E`, `∃I`, `∃E`, `=I`, `=E`. `∀E` and `=I` take a `TERM` param (`extraParameters.term`, parsed with `ParseFirstOrderAction.parseTerm`; a missing one is a 400 "needs a term"); the targets of `∀I`/`∃I`/`=E` are `EXPRESSION`s. Steps have no `extraParameters`, and proof text uses the plain layout (`=I` with no lines, `∃E [1, 2-4]`). `FirstOrderExercises` is the first-order catalog (quantifier swaps, `∀`/`∧` distribution, symmetry and transitivity of `=`), plus six group exercises (`group-...`) whose premises are exactly `FirstOrderTheories.GROUP_AXIOMS`, the `group` theory (`m` the operation, `e` the identity, a free name acting as a constant, `i` the inverse); the catalog is ordered by difficulty as a whole, and the premises are how a client tells the group ones apart. The UI offers it (see the frontend section below).

**`"modal-next-until"`** (`ModalNextUntilConfiguration`, package `com.dan323.uses.modal.nextuntil` in `modal-use-case`; domain in `com.dan323.proof.modal.nextuntil`) extends modal logic the other way: more rules, not fewer. It is modal logic over discrete states with Next `X A` (`A` in `s+1`) and strong Until `A U B`. States are `StateTerm`s (`s0`, `s0+1`, ...; `language.implementation.modal`), kept normalized (`s0 + 1` becomes `s0+1`) by the transformer's and parser's `parseState` hook. `ModalNextUntilLogicParser` reads `X`/`U` only as standalone words (so `TRUE`, `Xp`, `pUq` stay names). `ModalNextUntilNaturalDeduction` subclasses `ModalNaturalDeduction` (no longer `final`) and overrides `parse()`, `stateIsUsedBefore` (a state is used when its base is), `isFreshState` (the hook `[]I`/`<>E` call; the fresh state must be an unused base, not on the other side of its relation), `isDone` (the goal must be in `s0`) and `automate()`, which runs `LinearTimeAutomate` (`com.dan323.proof.modal.internal`; `hasSolver()` is true). Time is linear: `s <= t` holds when `t` is `s`, `s+1`, `s+2`, ..., which `Ind` needs and which makes `<> (X p) -> X (<> p)` a theorem. Besides `XI`, `XE`, `Succ`, `UI1`/`UI2` (shown as `UI`), `UE`, `U<>` and `Ind`, the logic has the rules of linear time of Bolotov's natural deduction for PLTL, adapted to state terms: `-U` (`-(A U B)` gives `([] (- B)) | ((- B) U ((- A) & (- B)))`), `UW` (from `A U B` in `s`, `s <= t` for an unused base `t`, the witness; like a fresh state it cannot be generalized over later), `UB` (from a `UW` line, `B` in `t`), `UA` (from a `UW` line, `A` in every `k` the relations put in `s <= k`, `k+1 <= t`), `Ord` (a relation, or `FALSE`, that the cited relations give in linear time; `StateOrder` reads relations as difference constraints on the bases: shortest paths give entailment, negative cycles contradiction), `Eq` (a formula moves between states the relations make equal) and `Lin` (close a subproof that assumes `u <= v` and ends in `FALSE`, derive `v+1 <= u`). `Ord`, `Eq` and `UA` find their relation lines when a client applies them and print them (`Ord [1, 2]`, or `Ord` with none). `LinearTimeAutomate` is the proof search of Bolotov, Grigoriev and Shangin (TIME 2007): a stack of goals; a reached goal applies the introduction rule it was set up for; else an introduction rule, else an elimination in the paper's order (`UW` only when `-B` holds in `s`, then it derives `s+1 <= t` at once), else subgoals from the goal's shape (a `|`, `<>` or `U` goal is first tried as a part, then refuted); a `FALSE` goal takes a missing premise from a line (not refuted in turn), then a `Lin` case split on two states, then, when a `[]` is in the proof, induction on a formula of the proof (goal `[] (A -> X A)`, then `Ind`). Unlike the paper it backtracks to the last open choice (replaying the kept lines, as `GoalDirectedAutomate.restore(State)` in the classical module does); it gives up with the premises only after `ROUNDS_PER_SYMBOL`/`STEPS_PER_SYMBOL` times the size of premises and goal (counts, not a wall-clock limit, so the answer does not depend on the machine; a search longer than the REST solve timeout is a 422); `XE` and the states it reasons on stop after as many successors as there are `X`/`U`. `ModalNextUntilSolverTest` solves every exercise (the induction one with `Ind`) and the goals the old solver missed, and `LinearTimeSolverSemanticsTest` checks it against the semantics on 300 seeded random formulas (`LassoChecker` looks for a countermodel among lassos of length <= 5): nothing with a countermodel is proved, and every sampled formula without one is. `ModalAutomate` (the `modal` solver, `final`) is not used by `modal-next-until`; `ModalSolverRegressionTest` (`modal-solver-proofs.txt`) pins its proofs. Its rules are read by `ParseModalNextUntilAction` before falling back to `ParseModalAction`. `ModalProofTransformer`/`ModalProofParser` expose protected hooks (`parseExpression`, `parseReason`, `parseState`, `parseWithReason`, `parseAction`, `newProof`, `actions`) whose modal defaults are the old behaviour; `"modal"` must stay exactly as it was (`ModalFreshStateTest`).

**Statelessness:** the server keeps no session. For every action the client sends the whole `ProofDto` plus an `ActionDto`. `Transformer.from(ProofDto)` rebuilds the domain proof by replaying each step's rule, then applies the new action and serializes back.

**Actions and the solver:**
- `GET .../actions` returns `ActionDescriptorDto`s (`name` + ordered `params` of `ParamKind` `INT`/`EXPRESSION`/`STATE`/`TERM`), built once at startup. Classical: `ClassicGetActions` maps every `AvailableAction` (its `switch` has no default, so a new action does not compile until described). Intuitionistic: `IntuitionisticGetActions`, the classical descriptors filtered by `AvailableAction.isIntuitionistic()`. Modal: `AvailableModalAction`, whose names are the rule names `ParseModalAction.parseAction` understands. First-order: `AvailableFirstOrderAction`, likewise for `ParseFirstOrderAction.parseAction`. `ActionDto.name` must equal a descriptor name, except that the 14 rules classical and modal share take either spelling in every logic (`COPY`/`Rep`, `MP`/`->E`, ...: `AvailableAction.fromName`/`getRuleName`, `ParseModalAction.ruleName` and `ParseFirstOrderAction.ruleName`; `SharedRuleNamesTest` checks they agree); the transformers turn it into the logic's descriptor name before `ActionExpression` checks it. `INT` params are the 1-based `ActionDto.sources`, in order; `EXPRESSION` goes in `extraParameters.expression`, `STATE` in `extraParameters.state`, `TERM` in `extraParameters.term`. The frontend `Menu` renders its inputs from the descriptor.
- `POST .../action` answers 200 with `ProofResponse(proof, success, done, message)`, or 202 with `success=false` when the action is well formed but does not apply (the returned proof is the replayed request proof without the action: same steps, but assumption levels recomputed by the domain, whatever levels the request sent; the frontend's `replayProof` (`service/actions.ts`: undo, the New Proof check and the restore after a reload) relies on this). `done` is the domain's `Proof.isDone()` (a top-level step equals the goal, not necessarily the last); the UI reads it instead of computing success itself.
- `POST .../solve` runs `Proof.automate()` via `LogicalSolver` on a daemon thread with a timeout (`natural-deduction.solve-timeout`, default 10s) and a cap on concurrent solves. An unfinished proof is still a 200 with `done=false`. A logic whose `Transformer.hasSolver()` is false gets a solver that throws `NoSolverException` (every logic has a solver now).
- Failures are `ErrorResponse{message}` from `RestExceptionHandler`: 404 unknown logic, 400 `InvalidProofException`/`InvalidActionException`/`NoSolverException`, 422 `SolveTimeoutException`, 429 `SolverBusyException`, 500 for anything else.

**Text protocols that span layers (edit these together):**
- Proof text files (`POST .../proof`) and `ProofStep.toString()` use a fixed layout: 3 spaces of indent per assumption level, an 11-space gap, then the rule, e.g. `->I [1-2]`. `ProofParser.ProofLine`/`parseLine` and `ProofReason.parseReason` depend on this. Frontend `proofToText` (`service/utils.ts`, "Copy proof as text") writes it, and `loadProofFromText` (`service/actions.ts`, "Load from text" in `NewProofModal`) posts it to this endpoint, so the UI only loads finished proofs: the last line is the goal, the leading top-level `Ass` lines are the premises. Frontend `ProofViewer` also regex-parses the `[1-2, 4]` part of rule strings for hover highlighting. Modal lines start with the step's state before the indent (`s1:    p           []E [1, 2]`, as `ProofStepModal.toString()` prints and `ModalProofParser.parseLine` reads); relation lines (`s0 <= s1`) have no prefix. `proofToText` writes the prefix from `extraParameters.state`.
- Line numbers in rules and in `ActionDto.sources` are 1-based.

**Java modules (JPMS):** every module has a `module-info.java`. A new package that another module needs must be `exports`ed, and new dependencies need a `requires`. Spring itself runs on the classpath, but the modules still have to compile.

## Frontend / build gotchas

- The frontend calls relative URLs (`/logic/...`). `vite.config.ts` proxies `/logic` (only that path) to `http://localhost:8080`, so `npm start` works next to a running backend jar. `constant.ts` holds `LOGICS`, the logics the UI offers.
- The UI offers the logics in `LOGICS` (`constant.ts`): `"classical"`, `"intuitionistic"`, `"modal"`, `"modal-next-until"` and `"first-order"`. Each entry has a static `hasSolver` (all five logics have a solver, so it is true for every entry; `MenuSolve.test.tsx` mocks `hasSolver` to test the no-solver hint), and the Menu shows Solve only when it is true. A solve that comes back unfinished with only the premises (the `modal-next-until`, intuitionistic and first-order solvers reset to them when they give up) leaves the proof on screen as it was, with a notice; any other unfinished answer replaces it ("Continue from where it stopped"). Everything logic-specific follows `proof.logic`: the Menu's rules (remounted per proof), Undo, the exercise list and solved ids (per logic), the saved proof (it keeps its logic; one of a logic not in `LOGICS` is discarded as corrupt), and the New Proof dialog (its selector starts at the current logic; Start Proof and "Load from text" use the one picked). Before a proof exists, the empty page's picker sets that logic for "Try an example" and the exercises.
- States (modal, `hasStates` in `constant.ts`): `ModalProofTransformer.initialAssumption` rejects a premise not in `s0`, so `App`'s `checkNewProof` (New Proof, the example, exercises) gives every premise `{ state: INITIAL_STATE }`, except a relation (`isRelationFormula`: its top-level operator is `<=` or `=`; `p & s0 <= s1` is not one), which gets `{}` as the backend returns it. `ProofViewer` adds a State column for such a proof. `AppModal.test.tsx` starts modal proofs against a mocked modal backend (`__test__/statesBackend.ts`, shared with `AppModalNextUntil.test.tsx`).
- `"modal-next-until"` in the UI (`AppModalNextUntil.test.tsx`): states can be successor terms (`s0+1`), shown, typed and written by `proofToText` as the backend normalizes them (the UI does not normalize). `connectives.ts` adds X and U buttons (typing `X ` and ` U `; `insertAtCursor` puts a space before `X` when a word character precedes the caret) and hint entries for that logic only. `checkFormula(formula, logic)` and `isRelationFormula(formula, logic)` read `X`/`U` as operators only as whole words and only for that logic, matching `ModalNextUntilLogicParser`'s tokenizer (`Xp`, `pUq`, `TRUE` stay names; in other logics `X p` is refused).
- `"first-order"` in the UI (`AppFirstOrder.test.tsx`): `checkFormula(formula, 'first-order')` is `checkFirstOrderFormula` (`service/firstOrderSyntax.ts`), a port of `FirstOrderParser`'s grammar (terms start lowercase, predicates are any name, `forall`/`exists`/`TRUE`/`FALSE` reserved, no infix operation on terms, so no `*`: a product is `m(x, y)`), so it accepts what the backend accepts; the other logics refuse `forall x. P(x)` (the `.`) and `P(x)`. `isRelationFormula` is always false there (no states; `x = e` is a formula). `renderExpression` shows `forall x.`/`exists x.` as `∀x.`/`∃x.` in every logic (only first-order has a variable followed by `.`). `connectives.ts` adds ∀, ∃ and = buttons (typing `forall `, `exists ` and ` = `; the word ones get a space before them after a word character, like `X`) and a hint for that logic only. The Menu renders a `TERM` param as a plain text input (no formula hint or buttons) and sends it in `extraParameters.term`. First-order steps have no `extraParameters`, so `proofToText` writes the plain layout unchanged (`=I` with no lines).
- Browser storage: `sessionStorage` key `natural-deduction.proof` (`service/savedProof.ts`) holds the proof on screen (`logic`, `goal`, `steps`, plus `exerciseId` when it was started from an exercise; never `done`, which is asked of the backend again on restore) so a reload keeps it. `localStorage` key `natural-deduction.solved-exercises` (`service/solvedExercises.ts`) maps each logic to the ids of its solved exercises. Unusable storage is ignored in both.
- Exercises UI: the "Exercises" button opens `ExerciseList` (from `GET /logic/{logic}/exercises`, grouped by difficulty, with a "Solved n of m" counter and a "(Solved)" marker). Starting an exercise (or "Next exercise") goes through the same in-page discard confirmation as New Proof when the current proof has more than its premises, and asks again if the proof changed (a rule, an undo) while the backend was checking the exercise. An exercise counts as solved when the backend's `done` is true for its proof.
- Theories (`fetchTheories` in `service/actions.ts`, `GET /logic/{logic}/theories`, cached per logic; a failed request or a malformed answer is no theories): `NewProofModal` (given `loadTheories`) shows a "Premises from theory" select only when the logic picked in it has theories (first-order: Group). Picking one replaces the premise rows with its premises, which stay editable; the select always returns to its placeholder. `App` fetches the theories after the exercises, and `ExerciseList` lists an exercise whose premises are exactly a theory's (in order) under that theory's own heading ("Group theory", after the difficulty groups, with its own difficulty subheadings), written `Group axioms ⊢ goal`; until the theories arrive, or without them, every exercise is listed by difficulty.
- The jar embeds the UI on its own: `executable/pom.xml` runs frontend-maven-plugin in `generate-resources` (downloads Node `node.version` into `executable/target/node`, `npm ci --ignore-scripts`, `npm run build` in `frontend/`) and packages `frontend/build` as `classpath:/public/`. So `mvn clean install`/`verify` always ship the UI of the checkout; `FatJarActionsIT.theFatJarServesTheCurrentUi` checks that the jar's bundle offers every logic. `-Dskip.installnodenpm -Dskip.npm` skips the frontend build (the jar then has no UI, or the last `frontend/build`, and that test is skipped); the PIT job uses it. `executable/src/main/resources/public/` (the old hand-copied UI, gitignored) is excluded from the jar, and `target/classes/public` is emptied at `initialize`, so a build without `clean` keeps no files of an older UI. Stop a running jar before rebuilding: the build cannot replace it while it runs.
- Backend `executable` runs `*IT.java` via a second surefire execution bound to `verify`, so plain `mvn test` skips them. `FatJarActionsIT` starts the packaged jar, so it only works through `verify`.
- The root pom's `spring.version` must match the Spring version that the Spring Boot parent of `executable/pom.xml` manages; `SpringVersionAlignmentTest` fails otherwise (e.g. after a dependabot Boot bump).
- `executable` does not inherit the root pom, so JUnit there comes from the Boot parent. Its `junit-jupiter.version` property overrides Boot's JUnit (6.0.x in Boot 4.1) to match the root `junit5.version` (JUnit 6). Bump both together.

## CI / Docker

- `CompileAndTest.yml`: `mvn verify` + Sonar + JaCoCo report, and a separate PIT mutation job (PIT settings live in the root pom's `pitest-maven` pluginManagement: `threads` 4 and a short `timeoutConstant`, because the mutants that make the automatic solvers loop forever each cost a full timeout; raise the timeout if healthy mutants ever show up as `TIMED_OUT`). `frontend.yml`: `npm ci --ignore-scripts` (Sonar rule; nothing in the tree needs an install script), `npm run typecheck`, `npm test`, Sonar. `OnMerge.yml` removes a closed PR's reports from gh-pages.
- `OnMaster.yml` ("Publish Docker image"): typechecks and tests the frontend, embeds it, runs `mvn verify`, then builds the image from that exact jar, smoke-tests it and only then pushes to Docker Hub. The smoke test checks `/logic/classical/actions`, `/logic/modal/actions`, `/logic/modal-next-until/actions`, `/logic/intuitionistic/actions`, `/logic/first-order/actions`, the UI and that the container user is not root.
- The `Dockerfile` copies `executable/target/*.jar`, runs as a non-root user and has a `HEALTHCHECK` on `/actuator/health`.
